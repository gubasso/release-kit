# Release setup

One-time bootstrap of this repository's release automation. Run once, in order: each step requires the one before it. Day-to-day releases: [release.md](./release.md).

Every step shows the command by hand first, then the `rk` step that runs the same thing. The hand form is the whole truth: `rk setup` executes exactly these calls, from the scripts under `setup/github/`, with four variables filled in. `rk setup script <name>` prints any of them for audit.

Nothing here needs `rk` on `PATH`. Everything here needs `gh` authenticated against an account that admins the project.

## Facts

| Fact               | Value                                                    |
| ------------------ | -------------------------------------------------------- |
| Project            | `gubasso/release-kit`                                    |
| Crate              | `release-kit`                                            |
| Integration branch | `develop`                                                |
| Release branch     | `master`                                                 |
| Required check     | `test`, the job name in `.github/workflows/ci.yml`       |
| Publish workflow   | `release-plz.yml`, the filename registered at crates.io  |
| Artifact workflow  | `release.yml`, generated by cargo-dist, never registered |
| Bot secrets        | `RELEASE_BOT_APP_ID`, `RELEASE_BOT_APP_PRIVATE_KEY`      |

The whole setup in one command, once the credentials in steps 6 and 8 exist:

```bash
rk setup --target .                                        # preview every step
rk setup --target . --apply --required-check test          # run them in order
rk setup check --target . --required-check test            # prove what was applied
```

## 1. Gate the package metadata

Before anything that needs a credential or cannot be undone. Packaging breaks long after setup, and a failure found here costs seconds where the same failure after the gate merge costs a recovery.

```bash
cargo publish --dry-run --locked
```

Automated: `rk setup step package-check --target .`

## 2. Make develop the default branch

Pushes to the default branch drive release-plz.

```bash
gh repo edit gubasso/release-kit --default-branch develop
# check: prints "develop"
gh repo view gubasso/release-kit --json defaultBranchRef -q .defaultBranchRef.name
```

Automated: `rk setup step default-branch --target . --apply`

## 3. Create master at develop's tip

Before its protection exists, so no rule governs the creation.

```bash
sha="$(gh api repos/gubasso/release-kit/git/ref/heads/develop -q .object.sha)"
gh api -X POST repos/gubasso/release-kit/git/refs \
  -f ref=refs/heads/master -f "sha=$sha"
# check: prints one sha for master
gh api repos/gubasso/release-kit/git/ref/heads/master -q .object.sha
```

Rerunning is safe. `gh api repos/gubasso/release-kit/compare/develop...master -q .status` is the guard: `behind` or `identical` is the normal state after a release and stays put, anything else is a branch this setup did not create and the automated step refuses to move it.

Automated: `rk setup step create-release-branch --target . --apply`

## 4. Delete main

Now that `develop` is the default and `master` exists, so no third long-lived branch remains. The comparison is the guard: a `main` that is not an ancestor of `master` holds work that deleting would lose.

```bash
gh api repos/gubasso/release-kit/compare/main...master -q .status   # ahead or identical
gh api -X DELETE repos/gubasso/release-kit/git/refs/heads/main
# check: prints nothing for main
gh api repos/gubasso/release-kit/git/ref/heads/main -q .ref
```

Automated: `rk setup step delete-main --target . --apply`

## 5. Let Actions write and open pull requests

So the workflow can act on `develop`.

```bash
gh api -X PUT repos/gubasso/release-kit/actions/permissions/workflow \
  -f default_workflow_permissions=write \
  -F can_approve_pull_request_reviews=true
# check: prints "write true"
gh api repos/gubasso/release-kit/actions/permissions/workflow \
  -q '"\(.default_workflow_permissions) \(.can_approve_pull_request_reviews)"'
```

Automated: `rk setup step ci-permissions --target . --apply`

## 6. Create the bot App

No command. The GitHub App manifest flow redirects through a browser, so this one is a web action; it happens once in an account's lifetime, never once per project.

`rk forge github` carries the walkthrough: which permissions to grant, which credentials to collect, and the warning that the private key downloads exactly once and is never shown again. Collect the App ID and the `.pem`, then continue.

## 7. Grant the App this repository

The installation endpoints refuse the OAuth token `gh auth login` mints, and the grant is documented for classic personal access tokens only.

```bash
installation="$(gh api /user/installations -q '.installations[0].id')"
repo_id="$(gh api repos/gubasso/release-kit -q .id)"
gh api -X PUT "user/installations/$installation/repositories/$repo_id"
# check: prints gubasso/release-kit
gh api "user/installations/$installation/repositories" --paginate \
  -q '.repositories[] | select(.full_name == "gubasso/release-kit") | .full_name'
```

Run it with `GH_TOKEN` holding a classic token carrying `repo` scope. Where the account has more than one installation, name the one to use rather than taking the first.

The web path takes one click and needs no token: open `https://github.com/settings/installations`, pick the bot App's installation, and add `gubasso/release-kit` to its repository access.

Automated: `GH_TOKEN=<classic-pat> rk setup step install-bot --target . --apply`

## 8. Store the bot credentials

Each value travels on standard input, because `gh` reads stdin when `--body` is omitted and `printf` is a shell builtin, so neither credential enters a process argument list. That is `forge-setup:a-secret-never-reaches-argv`, and it is why these are not `gh secret set --body`. The private key's PEM armor and newlines land verbatim.

```bash
printf '%s' "<the App ID>" \
  | gh secret set RELEASE_BOT_APP_ID --repo gubasso/release-kit
printf '%s' "$(cat /path/to/bot-private-key.pem)" \
  | gh secret set RELEASE_BOT_APP_PRIVATE_KEY --repo gubasso/release-kit
# check: lists both secrets
gh secret list --repo gubasso/release-kit
```

Overwriting is correct: a rotated credential must be able to replace an old one.

Automated: export `RK_BOT_APP_ID` and `RK_BOT_PRIVATE_KEY`, then `rk setup step bot-secrets --target . --apply`

## 9. Protect master

It takes no direct push: a pull request carrying a passing `test` check is the only way in, and that is the release gate. The merge method is a merge commit because GitHub offers no fast-forward merge, so a linear-history rule would reject every release merge and a rebase or squash would make `master` diverge from `develop` permanently. Nothing in the pipeline writes this branch, so it names no bypass actor.

```bash
gh api -X POST repos/gubasso/release-kit/rulesets --input - <<'JSON'
{
  "name": "master-protection",
  "target": "branch",
  "enforcement": "active",
  "bypass_actors": [],
  "conditions": {
    "ref_name": { "include": ["refs/heads/master"], "exclude": [] }
  },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": false,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": false,
        "require_extra_approval_for_unattributed_changes": false,
        "allowed_merge_methods": ["merge"]
      }
    },
    {
      "type": "required_status_checks",
      "parameters": {
        "do_not_enforce_on_create": true,
        "strict_required_status_checks_policy": false,
        "required_status_checks": [{ "context": "test" }]
      }
    }
  ]
}
JSON
# check: prints master-protection
gh api repos/gubasso/release-kit/rulesets \
  -q '.[] | select(.name == "master-protection") | .name'
```

To update in place rather than create, read the id first and `PUT` to `repos/gubasso/release-kit/rulesets/<id>` with the same body.

A wrong or missing check name does not fail here: it hangs the merge button on the gate with nothing saying why. `gh api repos/gubasso/release-kit/commits/HEAD/check-runs` lists the names this project's own workflow reports.

Automated: `rk setup step protect-release-branch --target . --apply --required-check test`

## 10. Protect develop

No force pushes, no deletion. It takes direct pushes and carries no required status check, because one would reject the push that opens a release; the release is gated on `master` instead.

```bash
gh api -X POST repos/gubasso/release-kit/rulesets --input - <<'JSON'
{
  "name": "develop-protection",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["refs/heads/develop"], "exclude": [] }
  },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" }
  ]
}
JSON
# check: prints develop-protection
gh api repos/gubasso/release-kit/rulesets \
  -q '.[] | select(.name == "develop-protection") | .name'
```

Automated: `rk setup step protect-integration-branch --target . --apply`

## 11. Protect the release tags

`v*` can be created but never moved or deleted. A published version is immutable is a method invariant, not a project choice, so the pattern is fixed.

```bash
gh api -X POST repos/gubasso/release-kit/rulesets --input - <<'JSON'
{
  "name": "release-tags",
  "target": "tag",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["refs/tags/v*"], "exclude": [] }
  },
  "rules": [
    { "type": "deletion" },
    { "type": "update" }
  ]
}
JSON
# check: prints release-tags
gh api repos/gubasso/release-kit/rulesets \
  -q '.[] | select(.name == "release-tags") | .name'
```

Automated: `rk setup step protect-tags --target . --apply`

## 12. Prove the protections

Exactly three rulesets, and `master-protection` still carrying the shape a release merge needs. A ruleset that rejects or corrupts that merge is invisible until the release merge; a fourth ruleset no step owns is protection nothing here can reproduce or explain.

```bash
# check: exactly develop-protection, master-protection, release-tags
gh api repos/gubasso/release-kit/rulesets -q '.[].name' | sort

id="$(gh api repos/gubasso/release-kit/rulesets \
  -q '.[] | select(.name == "master-protection") | .id' | head -n 1)"
gh api "repos/gubasso/release-kit/rulesets/$id" -q '
  "bypass actors:  \(.bypass_actors // [] | length)          expected 0",
  "pull request:   \([.rules[].type] | contains(["pull_request"]))       expected true",
  "status check:   \([.rules[].type] | contains(["required_status_checks"]))       expected true",
  "linear history: \([.rules[].type] | contains(["required_linear_history"]))      expected false",
  "merge methods:  \([.rules[] | select(.type=="pull_request") | .parameters.allowed_merge_methods] | first)  expected [merge]",
  "required check: \([.rules[] | select(.type=="required_status_checks") | .parameters.required_status_checks[].context] | join(","))    expected test"'
```

Automated: `rk setup step protections-check --target . --required-check test`, or `rk setup check --target . --required-check test`, which reports all eleven steps rather than these three.

## 13. Land the workflow files

The release configuration and the publish workflow come from the payload:

```bash
rk init --tech rust --target .             # preview
rk init --tech rust --target . --apply     # write, then fill the reported sentinels
```

This repository holds them already, recorded by `rk adopt` in `.release-kit/manifest.json`: `.github/workflows/release-plz.yml`, `release-plz.toml`, `dist-workspace.toml`, and `AGENTS.md`.

The artifact workflow is not in that list. cargo-dist generates `.github/workflows/release.yml` from `dist-workspace.toml`, and it does not exist here yet:

```bash
dist generate
# check: lists release.yml beside ci.yml and release-plz.yml
ls .github/workflows/
```

Never edit that file by hand — a hand edit is silently reverted at the next `dist generate`. Change `dist-workspace.toml` and regenerate.

## 14. Publish the first version by hand

A trusted publisher attaches to a package that already exists, so the first version goes up with a token.

Creating the token is a web action: no API, once per package. Open `https://crates.io/settings/tokens/new`, then scope it as narrowly as it goes.

- Name: `release-kit-bootstrap`
- Expiration: the shortest offered
- Scopes: `publish-new` only
- Crates: add the pattern `release-kit`. Patterns match per request, so a crate that does not exist yet is fine and the "matches no crate you own" warning is expected.

```bash
cargo login                      # paste the bootstrap token
cargo publish
# check: the registry serves the version
cargo info release-kit
```

## 15. Register the trusted publisher

No API, once per package. Open the crate's Settings tab at `https://crates.io/crates/release-kit/settings`, and next to Trusted Publishing click Add.

- Repository owner: `gubasso`
- Repository name: `release-kit`
- Workflow filename: `release-plz.yml`, never `release.yml`, which builds installers, and never `ci.yml`
- Environment: leave empty; the release job declares no environment

Check on the same page: the publisher is listed under Trusted Publishing.

## 16. Revoke the bootstrap token

So the package has exactly one publishing path. Open `https://crates.io/settings/tokens`, revoke the token from step 14, and check on the same page that it is gone.

## 17. Prove the automated path

Cut one release end to end, following [release.md](./release.md). Its verify step passing — the registry serves the new version, the tag exists, the branches agree — is what step 18 depends on.

## 18. Require trusted publishing

No API, once per package, and only now that one release has proven the OIDC path. Open `https://crates.io/crates/release-kit/settings`, enable "Require trusted publishing for all new versions", and check on the same page that it shows enabled.

From here crates.io rejects every token publish. The hand-publish escape in `rk method recovery` starts by turning this back off.
