# release-kit 0.8.4

- destinations: .release-kit/config.toml, .github/workflows/release-plz.yml, .github/workflows/release-please.yml, .github/workflows/release.yml
- action: operator-step

## What changed

The trunk's GitHub protections now live in two rulesets. The safety ruleset, `<trunk>-safety`, carries deletion and force-push protection and names no bypass actor. The trunk ruleset keeps the pull-request rule and the strict required check, and names the actors the recorded integration mode excuses: none under forge integration, and the repository-administrator role under local integration, for the deliberate direct trunk push. A bypass actor is recorded on a ruleset and excuses every rule in it, so this split is what keeps the deletion and force-push rules holding against every actor while the direct push goes through. The release App is an integration actor, holds no repository role, and reaches neither bypass, so it still cannot merge a release request the trunk has moved past.

The landed release workflows treat a merge the trunk refuses on policy as a successful no-op: the job names what the forge answered, leaves the request open, and ends green. They also encode configured workflow and check names safely, search every page of candidate requests, and run the push-side retry only after the request job succeeds.

## What to do

Run `rk upgrade --target . --apply` and inspect the landed diff. Then run `rk setup step protect-trunk --target . --apply`, which creates the safety ruleset and rewrites the trunk ruleset to carry the request rules alone. Finish with `rk setup check --target .` and confirm that `protect-trunk` reports the release-merge shape beside the safety ruleset.

The old ruleset is not renamed. If the target already carried its trunk rules under a different name, delete the leftover ruleset in the repository settings once the check is clean.
