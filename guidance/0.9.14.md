# release-kit 0.9.14

- destinations: .github/workflows/release.yml, .gitlab-ci.yml, cliff.toml, .release-kit/config.toml, .release-kit/manifest.json, .github/workflows/release-please.yml, release-please-config.json, .release-please-manifest.json
- action: operator-step

## What changed

The release engine ships in this release as `rk release request`, `rk release build`, and `rk release publish`, and the bash and python release pipelines now call it. No pipeline carries release shell any more:

- On GitHub, `.github/workflows/release.yml` keeps the `release-request` job, which runs `rk release request`, and its `tag-and-attach` job becomes `release`, which runs `rk release build`, `actions/attest`, and `rk release publish`. The release job's App token now also reads pull requests, because the build releases only the commit that merges the engine's request.
- On GitLab, `.gitlab-ci.yml` runs `release-request`, `build`, `provenance`, and `publish`. The `attach` job becomes `publish`. The rk jobs run on a Debian image pinned by digest in place of `alpine:3`, because the `rk` archive needs glibc, and they fetch glab 1.130.0 and git-cliff 2.14.2, each checked against its SHA-256.
- Each job installs `rk` at this release's version. Where the target records a development environment, each job takes the recorded setup or image and runs `rk` through the recorded prefix instead, so the environment must carry `rk`, and git-cliff 2.14.2.
- The release request moves from the branch `chore/release-v<version>` to one branch per base, `rk-release/<base>`, which a later commit refreshes in place.
- `profile.release.build.packages` now names `apt` packages on both forges. It named `apk` packages on GitLab before.
- The seeded `cliff.toml` comments now describe the engine. The configuration itself is unchanged.
- The record of a bash landing pins git-cliff 2.14.2, glab 1.130.0, and the Debian image.
- The python pair moves to the engine on GitHub and lands on GitLab. A python landing writes `.github/workflows/release.yml` on GitHub or `.gitlab-ci.yml` on GitLab, and seeds `cliff.toml`. It stops landing `.github/workflows/release-please.yml`, `release-please-config.json`, and `.release-please-manifest.json`. The engine writes every version through `uv version`, so the release request and a candidate cut carry `pyproject.toml` and `uv.lock` together.
- A python landing refuses where `[project] version` is dynamic or absent, or where the root holds no `uv.lock`.
- `profile.release.registry` now takes `pypi` or `none` for python. An absent answer reads as `pypi`. Under `none` the python pipeline uploads nothing to PyPI and requests no PyPI token.
- The python jobs install uv: the exact `required-version` the project names, else uv 0.13.7. On GitHub `astral-sh/setup-uv` 10.3.3 installs it, and the PyPI upload stays `pypa/gh-action-pypi-publish` in the `pypi` environment. On GitLab the jobs install it through the uv installer, and the `pypi` job signs PEP 740 attestations with pypi-attestations 0.0.31 and uploads with `uv publish` over trusted publishing, on GitLab.com alone.
- The bash and python pipelines gain a `release-candidate` job, which cuts a release candidate on a release line through `rk lines mint`, as the rust pipelines do. On GitHub, `.github/workflows/release.yml` takes a `workflow_dispatch` with the inputs `line`, `expect`, and `promote`, and its push jobs now run on a push alone. On GitLab, `.gitlab-ci.yml` gains a manual job with the variables `LINE`, `EXPECT`, and `PROMOTE`. The mint push releases the candidate through the release jobs: a GitHub prerelease, or a GitLab release whose description names the candidate on its first line, and for python the PyPI prerelease where the answer is `pypi`.
- Every GitLab release job of the bash and python pipelines now holds a resource group keyed by its branch, `release-request-<branch>`, `release-<branch>`, and `release-candidate-<branch>`, in place of the shared `release-request` and `release`, so a release on one line never waits on another line's.
- The record of a python landing adds setup-uv 10.3.3, uv 0.13.7, glab, the Debian image, and cosign, moves pypi-attestations to 0.0.31, and drops release-please and setup-python.

## What to do

1. On GitLab, where `.release-kit/config.toml` sets `profile.release.build.packages`, check that each name is the `apt` package of the tool, and change any `apk` name to its Debian name before the upgrade renders it.
2. Run `rk upgrade --apply`. It rewrites both pipelines and the record on its own.
3. Where a request from `chore/release-v<version>` is still open, close it and delete its branch. The first `release-request` run opens `rk-release/<base>` beside it otherwise.
4. Optionally copy the new comments into `cliff.toml` from `rk snippet bash/github/cliff.toml` or `rk snippet bash/gitlab/cliff.toml`. A landing never rewrites a seeded file.
5. On a python target, run `uv lock` and commit `uv.lock` where the root holds none, and write a static `version` into `[project]` where it is dynamic, before the upgrade.
6. On a python target that answers `pypi`, register the trusted publisher the new pipeline needs before the first release: on GitHub the workflow `release.yml` with the environment `pypi`, and on GitLab the namespace, the project, and the top-level pipeline file `.gitlab-ci.yml`. `rk setup check` names the form.
7. On a python target that landed the release-please files, the upgrade stops landing them. Delete `.github/workflows/release-please.yml`, `release-please-config.json`, and `.release-please-manifest.json` in the upgrade commit, because the workflow keeps opening its own release request while it stays.
8. After the first push that runs the new pipeline, check that `release-request` opened or refreshed one request from `rk-release/<base>`, and that its log names the `rk` version of this release. On GitLab, check that the `build` job reached `rk release build`, which proves the image, glab, and git-cliff installs.
9. On a target that keeps release lines, cut the next candidate through the new job: on GitHub run `gh workflow run release.yml --ref release/<line> -f line=<line> -f expect=<sha>`, and on GitLab run the manual `release-candidate` job of the line's pipeline with `LINE` and `EXPECT`. Check that the push it makes releases the candidate as a prerelease, or on GitLab as a release that names the candidate, and that `rk lines rc <line>` names it. The GitHub job pushes with the release App's token, which needs no new permission.
10. On a python target, check that the first engine request changes `pyproject.toml`, `uv.lock`, and `CHANGELOG.md`, and that `uv sync --locked` passes on it. After its merge, check that `rk release status` reads the page with the sdist and the wheel, each attested, and on PyPI the version with its attestations.
