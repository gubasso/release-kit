# release-kit 0.9.14

- destinations: .github/workflows/release.yml, .gitlab-ci.yml, cliff.toml, .release-kit/config.toml, .release-kit/manifest.json
- action: operator-step

## What changed

The release engine ships in this release as `rk release request`, `rk release build`, and `rk release publish`, and the bash release pipelines now call it. Neither pipeline carries release shell any more:

- On GitHub, `.github/workflows/release.yml` keeps the `release-request` job, which runs `rk release request`, and its `tag-and-attach` job becomes `release`, which runs `rk release build`, `actions/attest`, and `rk release publish`. The release job's App token now also reads pull requests, because the build releases only the commit that merges the engine's request.
- On GitLab, `.gitlab-ci.yml` runs `release-request`, `build`, `provenance`, and `publish`. The `attach` job becomes `publish`. The rk jobs run on a Debian image pinned by digest in place of `alpine:3`, because the `rk` archive needs glibc, and they fetch glab 1.130.0 and git-cliff 2.14.2, each checked against its SHA-256.
- Each job installs `rk` at this release's version. Where the target records a development environment, each job takes the recorded setup or image and runs `rk` through the recorded prefix instead, so the environment must carry `rk`, and git-cliff 2.14.2.
- The release request moves from the branch `chore/release-v<version>` to one branch per base, `rk-release/<base>`, which a later commit refreshes in place.
- `profile.release.build.packages` now names `apt` packages on both forges. It named `apk` packages on GitLab before.
- The seeded `cliff.toml` comments now describe the engine. The configuration itself is unchanged.
- The record of a bash landing pins git-cliff 2.14.2, glab 1.130.0, and the Debian image, and the record of a python landing pins git-cliff 2.14.2.

## What to do

1. On GitLab, where `.release-kit/config.toml` sets `profile.release.build.packages`, check that each name is the `apt` package of the tool, and change any `apk` name to its Debian name before the upgrade renders it.
2. Run `rk upgrade --apply`. It rewrites both pipelines and the record on its own.
3. Where a request from `chore/release-v<version>` is still open, close it and delete its branch. The first `release-request` run opens `rk-release/<base>` beside it otherwise.
4. Optionally copy the new comments into `cliff.toml` from `rk snippet bash/github/cliff.toml` or `rk snippet bash/gitlab/cliff.toml`. A landing never rewrites a seeded file.
5. After the first push that runs the new pipeline, check that `release-request` opened or refreshed one request from `rk-release/<base>`, and that its log names the `rk` version of this release. On GitLab, check that the `build` job reached `rk release build`, which proves the image, glab, and git-cliff installs.
