# release-kit 0.9.14

- destinations: .github/workflows/release.yml, .gitlab-ci.yml, cliff.toml, .pre-commit-config.yaml, .release-kit/config.toml, .release-kit/manifest.json, .github/workflows/release-please.yml, release-please-config.json, .release-please-manifest.json
- action: operator-step

## What changed

The bash and python pairs now release through the release engine in `rk`: `rk release request`, `rk release build`, and `rk release publish`. Rust keeps release-plz. No release pipeline carries release shell any more.

- The release request moves to one branch per base, `rk-release/<base>`, which each refresh force-pushes in place. The bash pipelines opened `chore/release-v<version>` before.
- On GitHub, `.github/workflows/release.yml` runs the `release-request` job and the `release` job. The `release` job runs `rk release build`, then `actions/attest`, then `rk release publish`, and it releases only the commit that merges the engine's request. Its App token now also reads pull requests. The bash `tag-and-attach` job becomes `release`.
- On GitLab, `.gitlab-ci.yml` runs `release-request`, `build`, `provenance`, and `publish`, and for python with the `pypi` answer a `pypi` job too. The bash `attach` job becomes `publish`. The jobs run on a Debian image pinned by digest, and fetch glab 1.130.0 and git-cliff 2.14.2, each checked against its SHA-256.
- Each job installs `rk` at this release's version. Where the target records a development environment, each job takes the recorded setup or image and runs `rk` through the recorded prefix, so that environment must carry `rk`, git-cliff 2.14.2, and for python the uv the project requires.
- The python pair moves from release-please to the engine on GitHub, and lands on GitLab for the first time. A python landing writes `.github/workflows/release.yml` or `.gitlab-ci.yml`, and seeds `cliff.toml`. It stops landing `.github/workflows/release-please.yml`, `release-please-config.json`, and `.release-please-manifest.json`. The engine writes every version through `uv version`, so the request and a candidate cut carry `pyproject.toml` and `uv.lock` together.
- A python landing refuses where `[project] version` is dynamic or absent, or where the root holds no `uv.lock`.
- `profile.release.registry` takes `pypi` or `none` for python, and an absent answer reads as `pypi`. Under `none`, the pipeline uploads nothing to PyPI and requests no PyPI token. The python jobs install the exact `required-version` the project names, else uv 0.13.7. On GitHub the PyPI upload stays `pypa/gh-action-pypi-publish` in the `pypi` environment. On GitLab the `pypi` job signs PEP 740 attestations with pypi-attestations 0.0.31 and uploads with `uv publish` over trusted publishing, on GitLab.com alone.
- `profile.release.build.packages` now names `apt` packages on both forges. It named `apk` packages on GitLab before.
- The bash and python pipelines gain a `release-candidate` job that cuts a candidate on a release line through `rk lines mint`, as the rust pipelines do. On GitHub it runs on a `workflow_dispatch` with the inputs `line`, `expect`, and `promote`, and the push jobs run on a push alone. On GitLab it is a manual job with the variables `LINE`, `EXPECT`, and `PROMOTE`. Every GitLab release job holds a resource group keyed by its branch, so one line never waits on another.
- An upgrade now removes a destination this release stops landing where its bytes still match the record, and names it `retired`. It keeps an edited file, a seeded file, and a state file, and names each `dropped`. So an unedited `.github/workflows/release-please.yml` goes with the upgrade, while an edited one, `release-please-config.json`, and `.release-please-manifest.json` stay.
- `rk status --check` fails with `predecessor-release-workflow` while a release workflow of another tool stands beside the engine workflow of a bash or python target on GitHub.
- The landed hook block, on every pair, admits the branch `rk-release/<base>` in the branch-name hook, so a changelog correction on the request branch can be committed. The status check no longer watches the release-please files.
- The seeded `cliff.toml` comments describe the engine, and the configuration itself is unchanged. The record pins git-cliff 2.14.2, glab 1.130.0, and the Debian image for both engine drivers, and for python also setup-uv 10.3.3, uv 0.13.7, cosign, and pypi-attestations 0.0.31. It drops release-please and setup-python.

## What to do

Each step that writes to the forge or the registry is the operator's, taken at the time with the operator's approval.

1. Before the upgrade, where a release-please request is open, close it and delete its branch. Where a request from `chore/release-v<version>` is open, close it and delete its branch too. Otherwise the first `release-request` run opens `rk-release/<base>` beside it.
2. Before the upgrade, on a python target, run `uv lock` and commit `uv.lock` where the root holds none, and write a static `version` into `[project]` where it is dynamic. On GitLab, where `.release-kit/config.toml` sets `profile.release.build.packages`, change each `apk` name to its Debian name.
3. Run `rk upgrade --apply`. Where it names `.github/workflows/release-please.yml` `dropped`, the workflow carries edits: delete it in the same commit, because it keeps opening its own release request. `rk status --check` fails until it is gone.
4. After the upgrade, delete `release-please-config.json` and `.release-please-manifest.json`. The upgrade keeps both, because the target owns their bytes, and nothing reads them any more.
5. Where the registry answer is `pypi`, register the PyPI trusted publisher for the new pipeline before the first engine release: on GitHub the workflow `release.yml` with the environment `pypi`, and on GitLab the namespace, the project, and the pipeline file `.gitlab-ci.yml`. `rk setup check` names the form. Then, on GitHub, remove the registration for `release-please.yml`.
6. Check what the landing wrote on its own: the bash pipelines, the python workflow or pipeline, and `cliff.toml` where it moved. A landing never rewrites a seeded `cliff.toml`. Copy the new comments from `rk snippet <tech>/<forge>/cliff.toml` where you want them.
7. After the first push that runs the new pipeline, check that `release-request` opened or refreshed one request from `rk-release/<base>`, and that its log names the `rk` version of this release. On GitLab, check that the `build` job reached `rk release build`. On python, check that the request changes `pyproject.toml`, `uv.lock`, and `CHANGELOG.md`, and that `uv sync --locked` passes on it.
8. On a target that keeps release lines, cut the next candidate through the new job. On GitHub run `gh workflow run release.yml --ref release/<line> -f line=<line> -f expect=<sha>`. On GitLab run the manual `release-candidate` job of the line's pipeline with `LINE` and `EXPECT`. Check that `rk lines rc <line>` names the candidate it released.
