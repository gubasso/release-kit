# release-kit 0.9.0

- destinations: AGENTS.md, GLOSSARY.md, .pre-commit-config.yaml, .release-kit/config.toml
- action: operator-step

## What changed

The rules that only shape how a project works are now one opt-in capability, the workflow guards, in `capabilities.workflow_guards`. They are the agent policy and commit policy lines of the `AGENTS.md` block, `GLOSSARY.md`, the hooks `conventional-pre-commit`, `rk-message`, `rk-branch-name`, `rk-worktree-location`, `rk-no-push-to-trunk`, and `no-commit-to-branch`, and the setup steps `merge-cleanup` and `branch-reminder`. A fresh landing takes none of them.

A record from an earlier release carries no answer for the guards. That is a pending answer, and it reads as kept: `rk upgrade` reports it once and keeps every guard the target carries unless the operator answers `off`.

The `AGENTS.md` block no longer carries the integration line, the issue line, or the worktree and branches lines, in any capability state. Starting work, integrating a branch, and the working-copy layout are the project's own workflow, and `rk integrate`, `rk issue start`, `rk worktree`, and `rk branches prune` stay as helper verbs. The block's setup line also drops its two sentences on reopening the setup.

## What to do

Decide whether this project keeps the workflow guards. To keep them, run `rk upgrade --workflow-guards on --target . --apply`. To drop them, run `rk upgrade --workflow-guards off --target . --apply`, and `GLOSSARY.md` stays on disk as the project's own file. Commit the block changes and `.release-kit/config.toml`, which records the answer.

Where this project relied on the removed integration, issue, or worktree lines, write the rules it keeps in its own part of `AGENTS.md`, outside the markers.
