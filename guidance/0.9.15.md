# release-kit 0.9.15

- destinations: .release-kit/config.toml, .github/workflows/release-plz.yml, .github/workflows/release.yml, .gitlab-ci.yml, .pre-commit-config.yaml, .github/workflows/pr-title.yml, .gitlab/ci/mr-title.yml, .github/workflows/pr-commits.yml, .gitlab/ci/mr-commits.yml, AGENTS.md, .release-kit/setup-proof.json
- action: operator-step

## What changed

The `[dev_environment]` table takes a new key, `rk`. Its default, `environment`, keeps today's route: each landed job that runs `rk` takes it from the recorded environment, which must carry it. With `rk = "installer"`, the table states that the environment carries no `rk`. Each job that runs `rk` then takes the recorded setup, installs `rk` at the landing version through the shell installer, and still runs it through the recorded prefix. The installer checks the archive's SHA-256 before it installs. On GitHub the job appends the install directory to `$GITHUB_PATH`. On GitLab the rust candidate job exports a directory of its own, and the bash and python base installs into the tool directory it already exports. The prefix keeps that PATH, so every tool `rk` calls still comes from the environment.

On GitLab, the installer runs the published GNU/Linux `rk`, so the recorded image must carry `ldd` and the glibc loader. A Debian or Ubuntu based image carries both. The bare `nixos/nix` image carries neither.

A table without the key renders the same bytes as before. An `rk` below 0.9.15 refuses a record that carries `rk = "installer"`.

`rk integrate` no longer runs a hook runner. Its gate points the seat's `HEAD` at the trunk commit, so the staged change is the squash. It then asks git to run the clone's hook with `git hook run pre-merge-commit`. git runs whatever hook the project's hook manager installed. The hook manager selects the files natively. For prek and pre-commit, those are the staged files of the squash, not every file. A clone with no `pre-merge-commit` hook fails the gate with git's own error.

A gate can leave the seat off its branch in three ways:

- A signal that stops `rk integrate` while the hook runs leaves `HEAD` at the trunk commit, with the branch's tree staged.
- A hook that commits leaves `HEAD` at its own commit. The integration refuses.
- A hook that stages a change leaves the index changed. The integration refuses.

The next `rk integrate` of that branch refuses until the seat is on its branch again. `method/04-recovery.md` gives the repair for each case.

The landed block names no runner. Its install comment adds `--hook-type pre-merge-commit`. Under local integration, its note teaches the `pre-merge-commit` stage and `.prekignore`. prek runs a nested `.pre-commit-config.yaml` as a project of its own, and `.prekignore` excludes it. Under local integration, a `.pre-commit-config.yaml` that the landing creates lists `pre-merge-commit` in `default_install_hook_types`. A plain install then arms the gate. A file that already exists keeps its own top level.

Under local integration, `rk-no-force-push-to-trunk` now reads the remote trunk with `git ls-remote`. It refuses a force push that drops a commit the clone never fetched. `guidance/0.9.12.md` said that the landed push guards hold under either runner. That was false for both runners. Where the clone lacks the remote tip, prek and pre-commit pass an ancestor of the pushed tip as the base, so the old guard passed. The fix holds under both runners, for a push that adds a commit. Neither runner runs any check for a ref when the clone lacks the advertised remote tip and no pushed commit is missing from the remote-tracking refs. git still runs the installed shim, but the shim runs no check. A pure rewind over an unfetched commit therefore reaches the remote unchecked. Only a forge rule that refuses a non-fast-forward push to the trunk covers that case.

Each verb now checks the tools that `rk` runs for it before it acts. One error names every missing tool and every tool below its floor. The floors rise to git 2.36.0, which added `git hook run`, and gh 2.57.0, which added `gh auth status --active`. `rk doctor` now runs `gh auth status --active` alone, with no retry.

`rk` now sends its own web requests and signs the GitHub App token itself. It needs neither curl nor openssl, and `rk doctor` lists neither. The overrides `RK_CURL_BIN` and `RK_OPENSSL_BIN` are gone. The requests trust the platform's certificate store. They also trust the first bundle file that `SSL_CERT_FILE`, `NIX_SSL_CERT_FILE`, or `CURL_CA_BUNDLE` names, and each directory that `SSL_CERT_DIR` names. The requests honor `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, and `NO_PROXY`, in either case, the lowercase name first. `NO_PROXY` takes a host, a domain, an address, or an address range. The App token request of `rk setup step install-bot` now goes through a proxy the environment names. The curl it replaced did not receive the proxy variables.

In a repository, `rk doctor` now reports whether a `pre-merge-commit` hook is installed. It also reports whether the hook manager that wrote each installed hook runs. `rk status` warns about each tracked `.pre-commit-config.yaml` below the root that prek would run as a project of its own. `rk status --check` does not fail on that warning.

On a bash or python target, a release request now opens only where a file the release packs changed since the last release tag, or where the release packs a different set of files. git-cliff reads only the commits that touch those files, and also the commits on `.release-kit/config.toml` where its declaration changed that set, for the version, the changelog, and the release notes. A `build:`, `ci:`, or `docs:` commit outside the package opens no request, and a change reverted before the release releases nothing. The request adds only the new section to `CHANGELOG.md`, and every released section keeps its bytes. The files `rk` lands, and `.release-kit/`, never count. The `rk.release-request` report moves to `rk.release-request/2`, with the tag compared and the number of packed files.

A bash release now ships what `[profile.release.build]` declares, through `include` and `exclude`, two lists of gitignore-style patterns read as Cargo reads them. With neither key, every tracked file ships. `VERSION` always ships, and the files `rk` lands ship only where `include` names them. `rk release build` packs the declared files of `HEAD` into a reproducible `dist/<name>-<version>.tar.gz` with its `.sha256`, where `<name>` is the last segment of the project path. It runs the optional `verify` command in the unpacked archive before anything publishes. `rk release build --list` prints the files the package holds, and `rk.release-build` moves to `rk.release-build/2`. The request job builds nothing and installs no build package. On GitLab, the `build` job alone installs the build packages.

`profile.release.build.command` is retired, and the `--build-command` flag is gone. A configuration or a record that still carries the key makes `rk release request`, `rk release build`, `rk upgrade --apply`, and `rk status --check` refuse before any write. An `rk` below 0.9.15 refuses a record that carries `include`, `exclude`, or `verify`.

On a python target, the request builds the sdist at `HEAD` and at the tag, and counts the tracked files it holds.

A release request now also needs a releasing commit, on every driver. It opens only where a commit since the last release tag that touched the packed files is typed `feat`, `fix`, or `perf`, or marks a breaking change. The other commits stay in the changelog of the next request. With no release tag, the whole history counts. `rk integrate` now counts `perf` as release intent too. `rk release eligible` prints the answer and its reason, or an `rk.release-eligible/1` report under `--json`, writes nothing, and reads no forge. The rust request job installs `rk`, runs the verb before release-plz `release-pr`, and skips `release-pr` with the reason logged. The verb refuses a workspace whose release-plz releases more than one package, and `release-plz.toml` gains no key. `rk message --check`, the `rk-message` hook, the title check, and under the rebase merge form the commit checks refuse a message that names a `RUSTSEC-`, `GHSA-`, or `CVE-` advisory under any other type, and `rk.message` moves to `rk.message/4`. The landed `AGENTS.md` block states the dependency convention.

A release now happens only on the operator's order. No landed job and no `rk` verb arms or merges a release request by itself, under either integration mode and either style. The release request stays open and collects changes until the operator merges it. A changelog correction on the request's branch is the last step before that merge, because the bot regenerates the request on every trunk push.

The rust GitHub workflow no longer arms the request. Under local integration it no longer carries the `release-gate` job, its `workflow_run` trigger, or the `checks: read` grant. The rust GitLab pipeline sends no merge call. `rk release request` sends no arm call, and its report `rk.release-request/2` carries no `armed` field.

`setup.required_workflow` is retired. It named the workflow that woke the gate. Every verb that reads `.release-kit/config.toml` refuses while the key is present, `rk release request` included. A landing record that still carries the parameter loads, and `rk upgrade` writes the record without it. `rk.profile/6` and `rk.stage/9` carry no `required_workflow` field, and `--required-workflow` is no longer a flag.

The setup step `auto-merge` is now `merge-on-order`. It disarms each open release request that an older `rk` armed and leaves every other request as it is. On GitHub it no longer sets `allow_auto_merge`, and `rk setup check` reports that switch without judging it. On GitLab it still asserts `only_allow_merge_if_pipeline_succeeds`, because that setting holds a person's merge behind a passing pipeline. `rk setup check` faults an armed release request and names the call that disarms it. The App installation needs `contents: write` and `pull_requests: write` alone. These changes make every older setup proof stale.

`rk release status` reports an armed release request as the symptom `request-armed`, with the call that disarms it, and exits non-zero. `rk status` and `rk status --check` stay offline and judge no arm.

The operator merges a trunk release with `rk release merge`. Without `--apply` it previews: the open release request against the trunk, the trunk tip, the request's head, the required check or the head pipeline for that head, and the version, in an `rk.release-merge/1` report. With `--apply` it dispatches the new merge job with exactly those values and waits for that one run. Every automatic pair lands the job. It runs as the release App on GitHub and as the bot on GitLab, and it merges with the head pinned. It refuses unless the caller holds the administrator role on GitHub or the maintainer role on GitLab, and unless the request, the trunk tip, and the check still match. A release line's request keeps the merge by a person.

The GitHub release workflows take a required `action` input, `candidate` or `merge`, with no default. A candidate dispatch now names `-f action=candidate`, and `line` and `expect` stay required by the candidate job itself. On GitLab, the release jobs run only in push pipelines, and the merge job runs only in the API pipeline that `rk release merge` creates with `RK_RELEASE_ACTION=merge`. On GitHub, `setup.required_check` now defaults to `gate` for a trunk release under either integration, and `rk setup check` asks an automatic release's App for `checks: read` again.

The `.envrc` line no longer moves the pin. The new verb `rk self-depend check` reads a cache under `$XDG_CACHE_HOME/release-kit/self-depend/`. It reads the latest release at most once a week per checkout, or one hour after a failed read, under an OS file lock that it never waits for. It warns on every directory entry while a newer release is out or the last read failed, writes nothing but its cache, and exits 0. `RK_DEVSHELL_SYNC=0` and a CI variable stop the check. `rk self-depend sync --apply` is now the operator's act: its default caller is `operator`, `--caller envrc` is a usage error, and under `DIRENV_IN_ENVRC`, which direnv sets while it evaluates an `.envrc`, it moves nothing, warns, and exits 1. The switch and CI no longer stop it. The daily stamp is retired. `rk.self-depend-status/3` reports `envrc_check` and `envrc_old_sync` in place of `envrc_sync` and `stamp`, `rk.self-depend-sync/3` drops `caller` and `stamp`, the `rk.self-depend-add/3` fragment id `envrc-sync` is now `envrc-check`, and `rk.self-depend-check/1` is new.

## What to do

1. Take this release first. Then, if the recorded environment carries no `rk`, add `rk = "installer"` to the `[dev_environment]` table of `.release-kit/config.toml`. On GitLab, first make sure that `dev_environment.gitlab.image` carries `ldd` and the glibc loader.
2. Run `rk upgrade --target . --apply`.
3. Run `rk status --check --target .`.
4. Commit the upgrade with its manifest.
5. Under local integration, add the `pre-merge-commit` stage to every check that must pass before the trunk.
6. Where the configuration sets `default_stages`, add `pre-merge-commit` there.
7. Where the configuration sets `default_install_hook_types`, add `pre-merge-commit` there.
8. In each clone, install the hook with the project's hook manager, for example `prek install --hook-type pre-merge-commit`.
9. On git 2.54 or newer, confirm the hook with `git hook list pre-merge-commit`.
10. On older git, read the install output of the hook manager. It names each hook it installed.
11. Where the project runs prek, list each directory that holds a nested `.pre-commit-config.yaml` in a root `.prekignore`.
12. Drop pre-commit from a development environment that carried it only for `rk integrate`.
13. Make sure that every host and CI image that runs `rk` carries git 2.36.0 or newer.
14. Make sure that every host that runs `rk` against GitHub carries gh 2.57.0 or newer.
15. Where a host or a job names a proxy, make sure that the proxy reaches `api.github.com`.
16. Where the proxy cannot reach it, list `api.github.com` in `NO_PROXY`.
17. Remove `RK_CURL_BIN` and `RK_OPENSSL_BIN` from every script that sets them.
18. Keep the forge rule that refuses a non-fast-forward push to the trunk.
19. If the recorded environment carries `rk`, leave its `[dev_environment]` table as it is.
20. On a bash target whose `.release-kit/config.toml` records `command` under `[profile.release.build]`, replace it once this release is installed, because an older `rk` refuses the new keys. Remove `command`. Add `include` or `exclude` to name the tracked files the release ships. If the command checked something, such as `make check`, add it as `verify`. For example, this table:

    ```toml
    [profile.release.build]
    command = "make dist"
    packages = "make"
    ```

    becomes:

    ```toml
    [profile.release.build]
    exclude = ["docs/"]
    verify = "make check"
    packages = "make"
    ```

    The verify command runs in the unpacked archive, so keep every file it reads in the package, here the `Makefile` and the `tests/` that `make check` runs.

    Then run `rk upgrade --target . --apply`. The last release tag names neither `include` nor `exclude`, so it packs every tracked file. A declaration that narrows that set changes the package, so the commit that records it opens one release request where its type releases, for example `fix(packaging): ship only src/`, and that request ships the narrower archive.
21. On a bash target, run `rk release build --list` before the first release. Check that the list holds what the project means to ship. Name `SECURITY.md` in `include` if the archive must carry it.
22. On a bash target that Nix packages, keep the package derivation in `nix/package.nix`, and let `flake.nix` only call it. Name `nix/package.nix` in the declaration, and leave `flake.nix` and `flake.lock` out. A lock update then releases only with a later change to a packed file.
23. On a python target, run `uv build --sdist`, then `tar -tzf dist/<name>-<version>.tar.gz`. If the list holds a file whose change must not open a release request, exclude it from the sdist. A hatchling sdist takes `exclude` under `[tool.hatch.build.targets.sdist]`.
24. Type dependency updates by what they change. An update that changes what ships is `fix(deps)`. One for development only is `chore(deps-dev)` or `build(deps-dev)`. A security update is always `fix(deps)`, also where it changes only a lock file the package ships, and its body names the advisory ID. rk lands no bot configuration, so set your bot to match.

    With Renovate, `:semanticPrefixFixDepsChoreOthers` types a lock-only update `chore`, so a shipped lock needs an override:

    ```json
    {
      "extends": [
        "config:recommended",
        ":semanticCommits",
        ":semanticPrefixFixDepsChoreOthers"
      ],
      "semanticCommitScope": "deps",
      "packageRules": [
        {
          "matchDepTypes": [
            "dev-dependencies",
            "devDependencies",
            "dependency-groups"
          ],
          "semanticCommitScope": "deps-dev"
        },
        {
          "matchJsonata": ["isLockfileUpdate = true"],
          "semanticCommitType": "fix"
        },
        {
          "matchUpdateTypes": ["lockFileMaintenance"],
          "semanticCommitType": "fix"
        }
      ],
      "vulnerabilityAlerts": {
        "semanticCommitType": "fix",
        "semanticCommitScope": "deps"
      }
    }
    ```

    The two lock rules belong only where the package ships its lock: a rust binary, or a python sdist that packs `uv.lock`. Elsewhere leave them out, so a lock-only update stays a `chore`.

    With Dependabot, `prefix-development` covers `pip`, `uv`, `npm`, and a few other ecosystems, but not `cargo`:

    ```yaml
    version: 2
    updates:
      - package-ecosystem: uv
        directory: /
        schedule:
          interval: weekly
        commit-message:
          prefix: fix
          prefix-development: chore
          include: scope
      - package-ecosystem: cargo
        directory: /
        schedule:
          interval: weekly
        commit-message:
          prefix: fix
          include: scope
    ```

    On `cargo`, a development update then reads `fix(deps-dev)`, which releases; group or retype those by hand. The `commit-message` settings apply to security updates too. A security update to a development dependency therefore arrives with `prefix-development` and the `deps-dev` scope, such as `chore(deps-dev)`. Its author retypes it to `fix(deps)` by hand and keeps the advisory ID in the body. Neither bot is held to the advisory rule by itself: check that the advisory ID reaches the squash body, and add it where it does not.
25. Before step 2, remove the `required_workflow` line from the `[setup]` table of `.release-kit/config.toml`. If `[setup.excluded_steps]` names `auto-merge`, remove that entry too. The step is now `merge-on-order`, which disarms each armed release request, so do not exclude it unless the forge cannot run it. Every verb refuses the configuration while either line is present.
26. After step 2, on a host that holds the bot's key, run `rk setup --target . --apply`. Its `merge-on-order` step disarms each open release request.
27. Run `rk setup checkpoint --target .`, and commit `.release-kit/setup-proof.json` with the upgrade.
28. Run `rk setup check --target .` and `rk release status --target .`. Make sure that neither reports an armed release request.
29. Do steps 25 to 28 before the first push or integration of the upgrade.
30. On GitHub, before step 26, give the release App `Checks: Read-only` on its own settings page, and approve the updated permissions on the installation.
31. On GitHub under forge integration, where `setup.required_check` was empty, step 2 records `gate`. If your check job has another name, set `setup.required_check` to it before step 2.
32. On GitLab, set **Settings** > **CI/CD** > **Variables** > **Minimum role to use pipeline variables** to `maintainer`, through the project API attribute `ci_pipeline_variables_minimum_override_role` or the settings page. `rk release merge --apply` creates its pipeline with variables, so `no_one_allowed`, the default for a new project in a new namespace on GitLab.com, refuses it. rk does not observe this setting.
33. Replace each script that dispatches a candidate with `gh workflow run` to pass `-f action=candidate`.
34. Merge each trunk release with `rk release merge --target . --apply` from now on.
35. Where the project pins rk in its devshell, move the pin from a shell first: `rk self-depend sync --target . --caller operator --apply`. Both an older rk and this one accept that form. Commit the pin.
36. Then run `rk self-depend clean --target . --apply`. It swaps the retired `rk self-depend sync --apply || true` line in `.envrc` for `rk self-depend check || true`. Commit `.envrc`. Do this after step 35, because an older rk does not know `check`, and the line fails silently behind `|| true`.
37. Remove the daily stamps that an older rk left: `rm -f "${XDG_STATE_HOME:-$HOME/.local/state}"/release-kit/devshell/*.stamp`. Remove nothing else there: the locks, the backups, and `pending.json` recover an interrupted pin move.
38. Run `rk self-depend status --target .`. Make sure that it reports the check line and no finding about the retired sync line.
