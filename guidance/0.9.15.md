# release-kit 0.9.15

- destinations: .release-kit/config.toml, .github/workflows/release-plz.yml, .github/workflows/release.yml, .gitlab-ci.yml
- action: operator-step

## What changed

The `[dev_environment]` table takes a new key, `rk`. Its default, `environment`, keeps today's route: each landed job that runs `rk` takes it from the recorded environment, which must carry it. With `rk = "installer"`, the table states that the environment carries no `rk`. Each job that runs `rk` then takes the recorded setup, installs `rk` at the landing version through the shell installer, and still runs it through the recorded prefix. The installer checks the archive's SHA-256 before it installs. On GitHub the job appends the install directory to `$GITHUB_PATH`. On GitLab the rust candidate job exports a directory of its own, and the bash and python base installs into the tool directory it already exports. The prefix keeps that PATH, so every tool `rk` calls still comes from the environment.

On GitLab, the installer runs the published GNU/Linux `rk`, so the recorded image must carry `ldd` and the glibc loader. A Debian or Ubuntu based image carries both. The bare `nixos/nix` image carries neither.

A table without the key renders the same bytes as before. An `rk` below 0.9.15 refuses a record that carries `rk = "installer"`.

## What to do

1. Take this release first. Then, if the recorded environment carries no `rk`, add `rk = "installer"` to the `[dev_environment]` table of `.release-kit/config.toml`. On GitLab, first make sure that `dev_environment.gitlab.image` carries `ldd` and the glibc loader.
2. Run `rk upgrade --target . --apply`.
3. Run `rk status --check --target .`, and commit the upgrade with its manifest.
4. If the environment carries `rk`, change nothing.
