# release-kit 0.8.2

- destinations: .pre-commit-config.yaml, .release-kit/config.toml, .release-kit/manifest.json
- action: landing-write

## What changed

Three things a landing writes on its own, all of them corrections a local-integration target surfaced.

The committed configuration now takes this binary's own comment on every key it rewrites, rather than keeping whatever comment the file already carried. A target keeps its configuration across upgrades while the values in it move, so the template's sentence about a key could outlive the answer it described: a target that moved to local integration read `# F: invariant, contains all four rules` beside two of them. Only the comments this template writes are replaced, the ones marked `# P:`, `# N:`, and `# F:`. A comment the operator wrote carries no marker and is left exactly where it stands, and a key whose comment the operator deleted stays without one. Expect several comments to change wording in one upgrade, because each had drifted since the release that last wrote its key.

The registry keys its code scanning pins on the provider as well as the driver. A pin may now name `supply-chain.code-scanning/<driver>/<provider>`, and the landing record carries the pins of the provider the target actually landed. A target on `codeql` drops `codeql-upload-sarif` and `semgrep-image` from its record, and a target on `semgrep` drops `codeql-init` and `codeql-analyze`. Neither target ran the tools it was recording, so neither loses a staleness baseline it was using. `actions/checkout` is keyed on the bare capability, because either provider checks out.

The landed worktree guard states why the main checkout takes no branch commit without naming a push. It said the forge trunk takes no direct push, which is true under forge integration and false under local integration, where pushing the trunk is exactly the operator's last step. It now says the main checkout holds the trunk.

`rk setup step protect-trunk` also stops asking for `--required-check` on a target whose `protection.owned_trunk_rules` carries no `required_status_checks` rule. The name feeds that rule alone, and local integration owns no such rule, so the prerequisite named a flag whose value reached nothing.

## What to do

Nothing. Run `rk upgrade --target . --apply` and commit the diff, as with any landing write.

Read the configuration diff before committing it rather than skimming past it. The comment refresh and the value writes arrive in the same hunk, and only the values are answers.
