# release-kit 0.9.1

- destinations: .release-kit/config.toml, .release-kit/manifest.json, .github/workflows/pr-title.yml, .github/workflows/pr-commits.yml, .gitlab/ci/mr-title.yml, .gitlab/ci/mr-commits.yml, .gitlab-ci.yml, .github/workflows/release-plz.yml, .github/workflows/release-please.yml, .github/workflows/release.yml, .pre-commit-config.yaml, AGENTS.md, GLOSSARY.md
- action: operator-step

## What changed

The Git workflow has a third parameter, `git.merge_form`, which says how the commits of a branch reach the trunk. `squash` writes one commit for the branch, as every earlier release did. `rebase` rebases the branch on the trunk tip and moves the trunk to it, so every commit of the branch reaches the trunk with its own message. A record written before the parameter existed reads as `squash`. A configuration with no `merge_form` key takes the recorded answer, and with no recorded answer the form is `squash`, so a project that never answers keeps the squash form and its bytes.

The landing record moves to schema 12 and records the form. `.release-kit/config.toml` gains the key `merge_form` under `[git]`, with its comment. The comments of `protection.allowed_merge_methods`, `protection.github.squash_title_source`, `protection.github.squash_body_source`, and `protection.gitlab.squash_option` now say that the merge form decides them. The floors judge `allowed_merge_methods` and `gitlab.squash_option` by the stated form: exactly `["squash"]` and `"always"` under `squash`, and exactly `["rebase"]` and `"never"` under `rebase`, where the two squash sources are not judged. A landing writes both keys with the form.

A squash target lands the same bytes as before, apart from those comments. A rebase target lands the commit gate in place of the title gate: `.github/workflows/pr-commits.yml` on GitHub, and `.gitlab/ci/mr-commits.yml` on GitLab, which the root `.gitlab-ci.yml` includes. The gate judges every commit of a request on each push and admits the bot's release request as the title gate does. Under the workflow guards, its `AGENTS.md` routing block says that every commit of a branch reaches the trunk with its own message, in place of the line that makes the request's title the commit message. Its release workflow arms the bot's request with a rebase merge, and on GitLab asks for no squash. `rk setup` then installs the rebase settings: on GitHub the rebase merge alone, the linear-history rule in the safety ruleset, the `pr-commits` check in place of the title check, and the repository's own `allow_rebase_merge` switch turned on, with no other merge switch touched, which both checks now judge so a repository that disallows rebase merges no longer reads as ready; on GitLab merge method `ff` with `squash_option = never` and no squash template. The GitLab `mr-commits` gate refuses any merge commit in the request's range, naming it, before the bot's title exemption applies to the message rules, because the `ff` method adds the branch's commits as they stand: rebase such a branch into a linear range before its request merges.

A forge gate now lands only where a request reaches the trunk: under forge integration, or under an automatic release, whose bot opens one. A project with `git.integration = "local"` and a release mode of `none` or `external` loses the title gate on its next upgrade: `.github/workflows/pr-title.yml`, `.gitlab/ci/mr-title.yml`, and the minimal `.gitlab-ci.yml` that includes it leave the record and stay on disk as the project's own. `rk setup` then requires no status check on the GitHub trunk ruleset, and sets GitLab's `only_allow_merge_if_pipeline_succeeds` to `false`, while no-deletion and no-force-push hold as before. Both checks judge that value in both directions on every GitLab project: `true` exactly where a forge gate lands, `false` where none does, and a missing value is a fault.

A project whose release mode is `none` changes in four more ways on its next upgrade. The routing block in `AGENTS.md` takes its workflow variant: a `## Workflow` heading in place of `## Releases`, and no line that gives a version, a changelog, or a tag as a reason. `GLOSSARY.md` drops the `full-implement` term. `.pre-commit-config.yaml` drops the `rk-no-hand-authored-tag` hook and the release files from the `rk-status-check` pattern, and its `conventional-pre-commit` hook drops `--force-scope`, because a scope is preferred there and not required: `rk integrate` and `rk message --check` accept a header with no scope, while every other release mode keeps the scope required, and `rk message --json` reports a missing one as the class `scope-missing` under schema `rk.message/3`. Where such a project integrates at the forge, its title gate, or its commit gate under `rebase`, accepts a header with no scope and carries no line about the bot deriving the version or the changelog, while the grammar, a present scope's shape, and the content guards still hold; the forge request guidance of `rk integrate` asks for a Conventional Commit whose scope is preferred. `rk setup` no longer applies `protect-tags`, and `protections-check` requires no release tag protection. A fresh landing also leaves the tag protection keys, `[security]` unless the reporting policy is requested, and `[setup.bot]` out of `.release-kit/config.toml`; an existing file keeps what it states.

Under local integration with the workflow guards, `.pre-commit-config.yaml` gains the trunk guards: `no-commit-to-branch` for the trunk at the pre-commit stage, and the pre-push hooks `rk-no-force-push-to-trunk` and `rk-no-merge-commit-to-trunk`. `rk integrate` moves the trunk with no commit hook, so the guard never stops it, and the operator's fast-forward push of the trunk passes. The sweep note now names `no-commit-to-branch` in its `SKIP` list under either integration mode. Under forge integration, the `rk-no-push-to-trunk` message now says the trunk is written through merged requests, whatever the merge form.

`rk init --workflow-only` and `rk upgrade --workflow-only` set the release mode `none`, local integration, the `linked-worktree` checkout mode, and the workflow guards in one flag, and record those four answers alone. A flag that contradicts one of them refuses with the reason `preset-contradiction`.

## What to do

Nothing for a project that keeps squash: `rk upgrade --target . --apply` writes `merge_form = "squash"`, the refreshed comments, and the record, and the project integrates as before. To change the form, run `rk upgrade --merge-form rebase --target . --apply`, delete the title gate file it released and left on disk, `.github/workflows/pr-title.yml` or `.gitlab/ci/mr-title.yml`, commit what it wrote with that deletion, and merge it. Then run `rk setup step protect-trunk --apply` and `rk setup check`, because the forge still holds the squash settings until the setup rewrites them.

A project with local integration and a release mode of `none` or `external`: after `rk upgrade --target . --apply`, run `rk setup step protect-trunk --apply` first, so the forge stops requiring what the old gate reported: on GitHub the trunk ruleset drops the required check, and on GitLab the setup turns off the pipeline requirement the old gate left on, which would otherwise hold every merge request once the old pipeline is gone. Then delete the title gate files the upgrade released, `.github/workflows/pr-title.yml` on GitHub, or `.gitlab/ci/mr-title.yml` and `.gitlab-ci.yml` on GitLab where no job of your own lives there, commit, and run `rk setup check`. Then run `pre-commit install --hook-type pre-commit --hook-type commit-msg --hook-type pre-push` so the trunk guards run. A release-less project that still holds the `release-tags` ruleset or a protected `v*` tag may delete it; `protections-check` neither requires nor faults it.
