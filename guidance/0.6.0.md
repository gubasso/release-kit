# release-kit 0.6.0

- destinations: .release-kit/manifest.json, .release-kit/config.toml
- action: operator-step

## What changed

The installed `rk` renders one release: its own. `rk payload` and `rk reconcile` no longer exist, `--to` and `--fetch` leave every command, and no `compatibility.toml` ships. A landing runs through `rk stage`, which writes the complete candidate beside the target for an agent to read, and through `rk init`, `rk upgrade`, or `rk adopt` with `--apply`, which render again from the installed binary and write the receipt last. `rk method landing` states the five steps and `rk guide landing` carries the commands.

The receipt at `.release-kit/manifest.json` is schema 7: no payload digest and no baseline digest, one current digest per destination, and a placement where the destination is a marked region. A receipt at schemas 1 through 6 reads as before and rewrites as schema 7 at the next landing. The comment beside `tech` in `.release-kit/config.toml` now calls the value the binding; the file is the target's own answers and an upgrade never rewrites it.

## What to do

Before you install 0.6.0, finish or abandon every stored plan the installed 0.5.0 or older binary holds. Run `rk reconcile list` with that binary. Apply a plan you still want with `rk reconcile apply <plan-id>`. A plan you decline stays under the state root as inactive evidence, and no later binary reads it.

Install 0.6.0 through the manager your project uses. Then run `rk stage --target .` and read the printed path. Compare `artifacts/` with the working tree, then run `rk upgrade --target . --apply`. Review the Git diff against the stage, run `rk status --check --target .` and the project's own checks, and only then run the `rk stage clean <path>` line the stage printed.

The inactive plans, runs, and release cache the older binary left under the state root are the operator's to remove. `rk guide landing` step 5 lists and removes one path at a time, after a review of its contents.
