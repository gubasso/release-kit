# release-kit 0.8.0

- destinations: .release-kit/config.toml, .release-kit/manifest.json, .pre-commit-config.yaml, AGENTS.md, GLOSSARY.md
- action: landing-write

## What changed

The authority that moves an implementation onto the trunk is now a recorded Git workflow parameter, `git.integration`, beside `git.checkout_mode`. It is `local` or `forge`, and the two axes are independent. `rk method integration` states the model and `rk guide integration` is the procedure.

An existing target changes nothing. A record written before this release carries no such key and reads as `forge`, which is the authority that target landed, so its hook block renders byte for byte what it already carries. The compiled default for a fresh landing is `local`.

The landing writes three things on its own. The record moves to schema 10 and carries `git.integration`. The configuration gains the key with its comment. `AGENTS.md` and `GLOSSARY.md` gain the integration vocabulary: the routing block's trunk line now resolves per mode, its bounded-action list names integrating a branch, and the glossary says how each term's integration step resolves.

A local-integration target renders a different hook block. The two guards that refuse a trunk commit and a trunk push do not render, because `rk integrate` writes the commit and the operator pushes the trunk, and the header names the pre-integrate contract instead: `pre-commit run --hook-stage manual --all-files`. Release-kit invokes that one line and reads no hook identifier, so the stage assignment stays the project's.

`rk integrate <branch>` is new. Under local integration it rebases the branch onto the trunk, runs the `manual` stage in the seat, and publishes one squash commit through a compare-and-swap that carries the tip it observed before the gate ran, so every refusal leaves the trunk where it stood. It reads the record rather than the committed configuration, because the record is what landed, and an edited configuration is pending input to the next landing. It never pushes, and a preview refreshes nothing. Under forge integration it runs the project's own `pre-push` stage by pushing the branch and then names the request command; opening the request stays the operator's action.

`rk setup` resolves one effective protection policy from what the target stated and the authority its record names, and the body a step sends, the observer that reads the answer back, and every prerequisite all read that one resolution. The GitHub trunk ruleset's rules are composed from `protection.owned_trunk_rules` rather than a fixed list, so what a run installs and what its check expects cannot disagree.

Two floored keys travel with the authority, and the landing writes them: `protection.owned_trunk_rules` and `protection.gitlab.push_access_level`. A local-integration target carries `["deletion", "non_fast_forward"]` and level `40`; a forge-integration target carries all four rules and level `0`. `rk upgrade --integration <mode> --apply` rewrites both, in either direction, so the committed configuration never states a policy its own floor table refuses.

A target that narrowed or widened either key keeps what it stated: the authority decides the pair only where the target never diverged from one mode's own defaults. Such a target sets the pair itself before changing the mode, and the floor table names the key when it does not. A target with no record reads as forge, so an existing project's setup is unchanged.

Who may make that push is the forge's own answer rather than a rule this convention installs. On GitLab it is `protection.gitlab.push_access_level`. On GitHub it is repository write access: a ruleset carries no allowed-pushers list, and the one mechanism that would name them is a bypass actor, which the empty-bypass floor forbids.

Both prune verbs now accept two proofs. A merged request whose recorded head equals the branch tip is unchanged. A local integration whose recorded branch tip equals it is the second, read from a clone-local ledger under the common git directory.

`.release-kit/manifest.json` moves to schema 10. A record at schema 9 or below reads through the same bounded conversion as before and answers `forge`.

Three machine outputs changed shape. `rk branches prune` and `rk worktree prune` replace each row's `request` field with `proof` and `proof_kind`, and both schemas move to `/2`. `rk integrate` emits `rk.integrate/1`.

## What to do

Nothing, for a target that keeps forge integration: take the landing and commit it.

To move a target to local integration, run `rk upgrade --integration local --apply`, commit the diff, and run `rk setup step protect-trunk --apply`, which rewrites the ruleset for the authority the record now names. The upgrade writes the two protection keys for you unless your target narrowed or widened them, in which case it keeps yours and the floor table names the key. Assign the checks that must pass before an integration to the `manual` stage in the project's own `.pre-commit-config.yaml`, outside the marked block.

A tool reading either prune verb's JSON reads `proof` where it read `request`, and `proof_kind` to tell the two proofs apart.
