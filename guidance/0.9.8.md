# release-kit 0.9.8

- destinations: .github/workflows/release-plz.yml, .github/workflows/release-please.yml, .github/workflows/release.yml, .gitlab-ci.yml, release-plz.toml, .release-kit/config.toml, dist-workspace.toml, .release-kit/setup-proof.json
- action: operator-step

## What changed

Every rendered GitHub release workflow passes the bot identity to `actions/create-github-app-token` through the `client-id` input instead of the deprecated `app-id` input. The stored secret keeps its name, `RELEASE_BOT_APP_ID`, and keeps the numeric App ID, which GitHub accepts as the issuer of the token. The rust driver's workflows run release-plz 0.4.3, the version that `versions.toml` pins: the GitHub action steps name it through their `version` input, and the GitLab job downloads that release. A target that records `[dev_environment]` runs the release-plz of its own environment.

A rust crate that publishes to no registry now has a recorded answer, `profile.release.registry = "none"`. Under it, the seed pairs `publish = false` with `git_only = true`, `package-check` does not apply, and `rk release status` reads the release page. `rk status --check` fails a `release-plz.toml` whose `publish` and `git_only` contradict each other or the answer.

`rk status --check` reports `dist-target-unbuilt` for each target of `dist-workspace.toml` that no job the gate needs builds with `dist build` before a merge. The Rust binding serves two gated jobs, `dist-plan` and `dist-build`, that build every target the plan lists. `rk release status` reports `tag-without-release` for each tag after the newest complete release of its line.

On a target with an automatic release and a forge, `rk status --check` now reads `.release-kit/setup-proof.json` and counts an absent, stale, or invalid proof as a violation. A landing that replaces a GitHub workflow names each secret that moved, and the setup step that stores a new one.

## What to do

1. If the crate publishes to no registry, set `profile.release.registry = "none"` in `.release-kit/config.toml`, and edit `release-plz.toml` to `publish = false` with `git_only = true`. A landing never rewrites that seeded file.
2. Run `rk upgrade --apply`.
3. If `rk status` reports `dist-target-unbuilt`, add the `dist-plan` and `dist-build` jobs of `rk binding rust` to the gate's `needs`, or drop the target.
4. Run `rk setup check --target .`, then `rk setup checkpoint --target .`. The proof then matches the setup contract after the answer and the upgrade moved it. A step this forge cannot run goes in `setup.excluded_steps` with its reason.
5. Run `rk status --check --target .`. Commit the upgrade, the configuration, and `.release-kit/setup-proof.json` together.
6. Change no bot secret. The secret names and their values stay as they are.
7. If the target records `[dev_environment]` and publishes to no registry, make sure that its environment carries release-plz 0.3.168 or later.
