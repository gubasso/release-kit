# release-kit 0.9.13

- destinations: .gitlab-ci.yml, .github/workflows/release.yml, .github/workflows/release-plz.yml, cliff.toml, .release-kit/config.toml
- action: operator-step

## What changed

`[setup.bot]` in `.release-kit/config.toml` has a new key, `name`, the bot identity's name. The landing writes it as `name = ""`, and empty takes the forge's default. No landed byte depends on it.

On GitLab, `rk setup step install-bot` chooses the bot identity from the forge and the tier. A self-managed or Dedicated instance and a paid GitLab.com namespace keep the project access token. A GitLab.com Free group gets a group service account that is a member of the project alone, named `release-bot-<project id>` by default. A Free personal namespace is refused before any write. The step sends the token scopes as a JSON array, which GitLab accepts.

The bash release pipeline on GitLab reads its commit identity from the token's own account, so the release commit links to the bot, and it pushes as `oauth2`.

Both bash release pipelines build first and tag last. The build job no longer tags: the job that attaches the assets creates the tag and the release together, after the build and the provenance exist, so a failed build leaves no tag. The build skips the commit that introduces `VERSION`, the baseline `0.0.0`, and a version the forge already released at another commit. A tag at another commit stops the attach job and names the recovery section. The landing rewrites `.gitlab-ci.yml` and `.github/workflows/release.yml` on its own.

`[profile.release]` takes a `[profile.release.build]` table for a bash release: `command`, the command that produces `dist/<name>.tar.gz` and its `.sha256`, `make dist` by default, and `packages`, what the release image installs first, `make` by default. An unanswered table stays absent and changes no landed byte. `rk setup check` now judges the command before the first release: a make command needs a makefile whose target resolves.

The seeded `cliff.toml` renders a null version as `unreleased` instead of failing. A landing never rewrites the seed, so a landed project edits it by hand.

`.release-kit/config.toml` takes a landing declaration, `[landing]` with `accepted_drift`, written as `accepted_drift = {}`. An entry names a rendered whole file the project deliberately edits, with a reason and the SHA-256 of the accepted bytes. `rk status --check` then reports the edit instead of failing on it, a further edit still fails, and a landing keeps the file and says whether its candidate moved. `rk status` reports `rk.status/15` and prints the digest of each drifted rendered file.

The rust driver's `release-plz.yml` on GitHub gains a `workflow_dispatch` trigger and a third job, `release-candidate`. A person who dispatches it for a release line mints the line's next release candidate through `rk lines mint`, and release-plz publishes that candidate to crates.io as a prerelease. With the `promote` input, the job writes the newest candidate's stable version instead, and the line's release request proposes it. The two push jobs now run on a push alone, and the release-request job opens no request while a line carries a candidate's version. With no `[dev_environment]`, the job installs `rk` at the version that landed the workflow. With one, it runs the `rk` of the environment.

The rust driver's `.gitlab-ci.yml` gains a manual `release-candidate` job on line pipelines. Run it with the variables `LINE`, the line's `<major>.<minor>`, and `EXPECT`, the full SHA of the line's tip, and `PROMOTE=true` to promote. It mints through `rk lines mint`, releases through release-plz, and writes a release description that names the candidate and its install command, because a GitLab release carries no prerelease badge. The release request job holds while a line carries a candidate's version. Every release job's resource group is now per branch, so one line's release no longer waits on another's.

## What to do

1. Run `rk upgrade --apply`.
2. In `cliff.toml`, replace `## [{{ version | trim_start_matches(pat="v") }}] - {{ timestamp | date(format="%Y-%m-%d") }}` with `## [{% if version %}{{ version | trim_start_matches(pat="v") }}{% else %}unreleased{% endif %}]{% if timestamp %} - {{ timestamp | date(format="%Y-%m-%d") }}{% endif %}`.
3. If the project builds its tarball with another command than `make dist`, set `[profile.release.build]` `command` and `packages` in `.release-kit/config.toml` and run `rk upgrade --apply` again.
4. If the project's bot is a service account that you created by hand, set `setup.bot.name` in `.release-kit/config.toml` to its username.
5. Run `rk setup check --target .`. If it reports `install-bot` unsatisfied, run `rk setup step install-bot --target . --apply`, as a project Maintainer for a token or as the top-level group Owner for a service account. If it reports `package-check` unsatisfied, write the makefile or set the build command that its detail names.
6. If the project skips the status hook because it must edit a rendered file, add an entry under `accepted_drift` with the reason and the digest `rk status` prints, and drop the skip.
7. If a rust target records `[dev_environment]`, make sure that its environment carries `rk`. `rk self-depend` adds it.
8. Change no secret for a release candidate. On GitHub the job uses the release bot's existing App secrets, and on GitLab `RELEASE_BOT_TOKEN`. The existing crates.io trusted publisher covers it, because it names this same workflow file on GitHub and the top-level pipeline file on GitLab. A GitLab publisher that names an environment needs that environment on the `release-candidate` job too.
9. Run `rk setup checkpoint --target .` where the name is set, because the setup proof carries it, and commit `.release-kit/setup-proof.json` with the upgrade.
