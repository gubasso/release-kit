# release-kit 0.7.0

- destinations: .github/workflows/scorecard.yml, .github/workflows/code-scanning-codeql.yml, .github/workflows/code-scanning-semgrep.yml, .gitlab/ci/code-scanning-semgrep.yml, .gitlab-ci.yml, .release-kit/config.toml, .release-kit/manifest.json
- action: operator-step

## What changed

This release adds two opt-in landing capabilities and moves the receipt to schema 8.

`rk init --scorecard` lands `.github/workflows/scorecard.yml` on a GitHub target. The workflow computes an OpenSSF Scorecard result and publishes it to the public Scorecard API. The capability is off by default, because a run posts to a public API and reads repository metadata.

`rk init --code-scanning codeql` and `rk init --code-scanning semgrep` land one static analysis workflow. On GitHub the destination is `.github/workflows/code-scanning-codeql.yml` or `.github/workflows/code-scanning-semgrep.yml`; on GitLab it is `.gitlab/ci/code-scanning-semgrep.yml`, and `codeql` refuses that forge by name. `codeql` reads the licence the binding declares and refuses the pair where its terms do not cover the codebase. `semgrep` carries no licence condition.

The rendered `.gitlab-ci.yml` gains one include for the scanning job, guarded by `rules: - exists:` naming the same path. A GitLab target that did not opt in has no such file, and the include never fires. Every GitLab target takes this change, whether or not it wants the capability.

`rk status` gains a warning channel. A licence that lapses after the landing reports under the code `code-scanning-licence`, and `rk status --check` still exits 0: the target is not broken and the licensing decision is yours.

The receipt gains two parameters, `scorecard` and `code_scanning`. A receipt written by an earlier release names neither and reads as the opt-out, so an upgrade adds no workflow the target did not request. The first successful landing rewrites the receipt at schema 8.

`.release-kit/config.toml` gains `landing.scorecard` and `landing.code_scanning` in the `[landing]` table. An upgrade over an existing configuration inserts each key without the explanatory comment the fresh template carries.

Every machine report's schema moves with the parameters: `rk.init/9`, `rk.upgrade/9`, `rk.adopt/9`, `rk.status/11`, and `rk.stage/3`.

## What to do

Nothing is required. An upgrade records the opt-out and lands no new file.

To take the capability, run the upgrade with the flag:

```bash
rk upgrade --scorecard on --target . --apply
```

Read `rk forge github` first. It states what a Scorecard run can and cannot score under this convention, so the ceiling is known before the workflow lands.

Where the target already runs a Scorecard workflow of its own, stage the candidate and compare it with that file before the landing. Two workflows publishing one score is a collision the receipt cannot describe.

To drop the capability, run `rk upgrade --scorecard off --target . --apply`. The destination leaves the receipt and the file stays on disk as the project's own.

To take code scanning, read `rk binding rust` first. It states which field the licence is read from, and which three providers were refused and why. Then run the upgrade with the provider:

```bash
rk upgrade --code-scanning semgrep --target . --apply
```

`rk upgrade --code-scanning off --target . --apply` drops it the same way. Switching provider retires the other destination and leaves its file on disk.

A GitLab target takes the pipeline include whether or not it opts in. Run `rk upgrade --target . --apply` and commit the rewritten `.gitlab-ci.yml`.
