# release-kit 0.8.7

- destinations: AGENTS.md
- action: operator-step

## What changed

`rk setup checkpoint` observes every setup step and, only where every applicable step holds, writes `.release-kit/setup-proof.json`: the setup contract it observed, when, by which `rk`, and each step's normalized result, with no secret and no machine path. `rk setup status` judges that proof against the target offline, with no forge call and no key, and reports it compatible, stale with the changed fields named, invalid, or absent.

`rk setup check` now reads a key file this runtime cannot reach as an unknown `install-bot` rather than a refusal, and observes every other step. A check whose only gaps are unknown steps exits 1 with the reason `observation-incomplete`, names where the observation can be repeated, and prescribes no apply. A step found unsatisfied still names its remedy, and it supersedes any committed proof. `rk setup --apply` and `rk setup checkpoint` still refuse a key they cannot reach.

The landed `AGENTS.md` block gains one rule: an agent runs `rk setup status` before it reads a setup gap as a defect, and never asks the operator to expose a secret only so a check can pass.

## What to do

Run `rk upgrade --target . --apply` and commit the block change. Then, once, on a host that holds the bot's key, run `rk setup checkpoint --target .` and commit `.release-kit/setup-proof.json`. Isolated runtimes read `rk setup status --target .` from then on. After any change to the setup configuration, `rk setup status` names the changed field, and the checkpoint runs again.
