# release-kit 0.12.0

- destinations: .release-kit/config.toml, .release-kit/setup-proof.json, .github/workflows/release-plz.yml, .github/workflows/release.yml, .gitlab-ci.yml
- action: operator-step

## What changed

The `[protection]` table of `.release-kit/config.toml` takes four new keys: `updates_ruleset`, `tag_creation_ruleset`, `release_branch_ruleset`, and `release_environment`. The first three name the rulesets of the new protections, the last names the GitHub environment of the release bot secrets, and each has a default.

Only the release actors now change the refs that start a release or update the trunk. The release actors are the repository administrator and the release App, where an App ID resolves. Every other identity with write access is refused there.

On GitHub, `protect-trunk` adds the ruleset `<trunk>-updates`, which carries the update rule alone. The release App merges an ordered release request with an explicit bypass of the update rule alone, and the request rule and the required checks still bind it, so the merge job now passes `--admin` to `gh pr merge`. `protect-tags` adds `release-tag-creation` beside the immutable `release-tags`. On a Rust target it covers every tag that carries an `x.y.z` version with `refs/tags/**/*[0-9].[0-9]*.[0-9]*`, because the generated artifact workflow starts on such a tag, such as `x/1.2.3`. The pattern covers the release-plz tags, `v1.2.3` and `my-crate-v1.2.3`. A tag with no such version, such as `docs-snapshot`, stays open. The release branch patterns take the same `**/*` form, so a nested name such as `release/a/b` is covered too. The creation ruleset names the release App as a bypass actor, so the App token of the release jobs keeps `Contents: write` alone, and the comments of the release workflows say so.

The new step `protect-release-branches` covers the release lines and the head branches of both release requests, `release-plz-` and `rk-release/`. On GitHub it is one ruleset with the creation and update rules. On GitLab each pattern is protected at Maintainer for a push and a merge, with force pushes off.

On GitLab, `protect-tags` protects the recorded `protection.tag_pattern`, `v*` or `*`, with one create grant at Maintainer, and `ci-permissions` keeps merge request pipelines away from the protected variables and runners. The floor of `protection.gitlab.merge_access_level` rises from 30 to 40, so a recorded value below 40 refuses when `rk` reads the configuration.

Only the release refs now read the release bot secrets. On GitHub, every job of the release workflow that mints the release App token names the environment `release`. The python release job keeps `pypi` where it publishes. `bot-secrets` stores both secrets there, behind a deployment policy that admits the trunk, the release lines, the release request branches, and the release tags. It removes the repository copies once the trunk and every live release line run a workflow that names the environment. A private repository on the Free plan holds no environment secrets, so there the secrets stay repository secrets, and the checks name that limitation. On GitLab, `RELEASE_BOT_TOKEN` is now a protected variable, and `bot-secrets` protects a stored token in place, with its stored value.

On GitHub, both dispatch jobs, `release-candidate` and the merge job, run only on their own ref and only for an administrator.

On GitHub, `rk` now finds the bot's private key at one default path, `${XDG_CONFIG_HOME:-$HOME/.config}/release-kit/bot/github/<app-id>.pem`, where `<app-id>` is the resolved App ID. `RK_BOT_PRIVATE_KEY_FILE` still wins for one run, and the user configuration file `${XDG_CONFIG_HOME:-$HOME/.config}/release-kit/config.toml` can name another path per App ID under `[bot.github.private_key_files]`. `rk setup import-key <downloaded.pem>` moves a downloaded key to the default path with mode 0600. The App ID resolves from `RK_BOT_APP_ID`, then from `setup.bot.app_id`. So the `RK_BOT_*` exports in a project's own environment file are no longer needed. Where the key file is not readable by the current process, `rk setup check` reports `install-bot` and `bot-secrets` as `unreadable` with the remedy, and does not fail on them.

On GitHub, `protections-check` owns the three new rulesets and judges where the bot secrets live. On GitLab, it judges the tag pattern, the release branches, the merge request pipeline setting, and the protected flag of the bot token. A setup proof from an older `rk` is stale.

## What to do

1. On GitLab, if `.release-kit/config.toml` sets `protection.gitlab.merge_access_level` below 40, set it to 40.
2. Run `rk upgrade --target . --apply`.
3. On GitHub, where `setup.bot.app_id` is empty, set it to the release App's numeric ID and commit it. Without an App ID, the new rulesets name the administrator alone, and the release App cannot merge an ordered release request.
4. On GitHub, where the key lives in a file that no override names, run `rk setup import-key --target . <file>` once on each machine that runs the setup. A key that already stands at the default path needs no import. Then remove `RK_BOT_APP_ID` and `RK_BOT_PRIVATE_KEY_FILE` from the project's own environment file.
5. Where the project's own release automation pushes a release tag, a release line, or a release request branch under another identity, move it to the release App. Every other automation keeps an identity of its own, never the release App's key, and the forge now refuses that identity on those refs.
6. Where a job of the project's own reads `RELEASE_BOT_APP_ID`, `RELEASE_BOT_APP_PRIVATE_KEY`, or `RELEASE_BOT_TOKEN` outside the landed release jobs, or on a ref that is not a release ref, it stops getting them once the setup runs. Move that job onto a release ref, in the `release` environment on GitHub, or give it an identity of its own.
7. On GitHub, tell every collaborator with the write or maintain role that only the administrator now merges into the trunk and dispatches `release-candidate` and the merge job. Run `rk release merge` and `rk lines mint` as the administrator.
8. On a Rust project on GitHub, the creation ruleset covers every tag that carries an `x.y.z` version, not only the release-plz tags. Move every other push of such a tag to the administrator or the release App, or stop it.
9. Commit the upgraded workflows, and bring them to the trunk and to every live release line. Until each of those refs names the environment, the repository copies of the bot secrets stay, so no release job there loses them.
10. Where the bot's private key is readable, run `rk setup --target . --apply`.
11. On GitLab, if the setup stops with "the stored RELEASE_BOT_TOKEN cannot be read back to protect it", export `RK_BOT_TOKEN` with the bot token, and run `rk setup step bot-secrets --target . --apply`. The step then stores that token protected.
12. Run `rk setup checkpoint --target .`, and commit `.release-kit/setup-proof.json` with the upgrade.
13. Run `rk setup check --target .`, and make sure that it reports `protect-release-branches`, `bot-secrets`, and `protections-check` satisfied. Where it names refs that still run the old workflow, bring the upgraded workflow there, and run step 10 again.
