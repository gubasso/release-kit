# release-kit 0.8.3

- destinations: .release-kit/config.toml, .release-kit/manifest.json, .pre-commit-config.yaml, .github/workflows/release-plz.yml, .github/workflows/release-please.yml, .github/workflows/release.yml
- action: operator-step

## What changed

Under local integration the trunk carries no required-check rule, because a ruleset carrying one rejects the direct push that mode exists to make. That same rule was what held the release request until continuous integration concluded, so dropping it left the request mergeable the moment it opened. The hold now lives in the landed release workflow instead.

Two configuration keys carry it. `setup.required_check` was a name `rk setup` resolved and nothing recorded; it is now a landing parameter, because the rendered gate reads it. `setup.required_workflow` joins it and names the workflow whose completion wakes that gate, by the workflow's own `name` and never by its filename. Both are written back and recorded, and where nothing answers them at the one shape that renders a gate — GitHub, an automatic release, the trunk style, local integration — the landing resolves this convention's own pair, `gate` and `ci`.

A GitHub target under local integration lands a changed release workflow. It gains a `workflow_run` trigger on the recorded workflow, every job written for a push gains a guard that keeps the new event out of it, the standing `--auto` arm goes, and one `release-gate` job takes its place. That job reads the candidate back from the forge, requires it to be open, not a draft, based on the trunk, headed from this repository, and authored by the release app, then judges the named check for that exact head and merges with `--match-head-commit`. Under forge integration every byte of the release workflow is unchanged, because there the ruleset still holds the request. GitLab is unchanged either way: its own auto-merge already waits for the whole pipeline.

Reading a check run widens the release app's minimum grant. `install-bot` now reads the installation's own permissions and reports unsatisfied naming each one the target's release automation needs and the installation lacks.

The landed hook block's notes gain the second axis. A check has a scope as well as a stage: `both`, `local-only`, or `ci-only`.

## What to do

Run `rk upgrade --target . --apply` and read the configuration diff before committing it. Two keys move, and `required_check` changes its class marker from `N` to `P`.

On a GitHub target under local integration, do two more things.

Set `setup.required_workflow` to the `name:` of the workflow that reports your gate check, and `setup.required_check` to the context that workflow's gate job reports, unless `ci` and `gate` are already those names. Then run `rk setup check --target .` and read `protect-trunk`: it faults where the named workflow does not carry the named check or does not run for a request against the trunk. A wrong pair refuses every release silently, because the gate either wakes before the check can report or never wakes at all.

Open the release app's installation settings page and approve its updated permissions. The app now asks for `Checks: Read-only` beside its two writes. `rk setup check` reports `install-bot` unsatisfied and names the missing permission until that approval lands, and no token a workflow mints can grant it.
