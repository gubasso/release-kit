# release-kit 0.10.1

- destinations: AGENTS.md, flake.nix, .claude/skills/rk-setup/references/upgrade.md, .claude/skills/rk-setup/references/provision.md, .agents/skills/rk-setup/references/upgrade.md, .agents/skills/rk-setup/references/provision.md
- action: operator-step

## What changed

rk now says where a pin move is due and how to take it. `rk self-depend check`, `rk self-depend status`, and `rk status` warn when the pin is behind the latest release that the check cache records. `rk doctor` reports the same in its soft probe `pin-freshness`. None of them reads the network. `rk status --json` reports the pin under the field `pin`, in the schema `rk.status/16`.

After a pin move, `rk self-depend sync`, the `rk upgrade` preview from a newer binary, and the version gate route the reader through the setup skill of the new rk. The managed block of `AGENTS.md` carries the same route as one more bullet. The block grows by one line. An `AGENTS.md` near its line budget loses that line of room.

`rk self-depend status` and `sync` name each follows line that the `release-kit` input of `flake.nix` lacks, from `flake.lock`. Nothing writes the lines. The flake fragment of `rk self-depend add` and its seed flake carry `inputs.release-kit.follows = "";`.

## What to do

1. After the pin move, load the devshell and run the upgrade through the rk-setup skill of the rk in that devshell, and do every migration it names. Before `rk upgrade`, read it with `rk skill show rk-setup`. After it, the project's .claude/skills/rk-setup is that skill. Never use a host copy or an older skill.
2. Run `rk upgrade --target . --apply`. It adds the bullet to the managed block of `AGENTS.md` and refreshes the skill files.
3. If the line budget of `AGENTS.md` fails, shorten the project's own text outside the managed block.
4. Run `rk self-depend status --target .`. If its `next` names follows lines, add each to the `release-kit` input of `flake.nix`, beside its `url`, then run `nix flake lock`.
5. Commit the files with the receipt.
