# release-kit 0.10.0

- destinations: .release-kit/manifest.json, .claude/skills/rk-setup/SKILL.md, .claude/skills/rk-release/SKILL.md, .agents/skills/rk-setup/SKILL.md, .agents/skills/rk-release/SKILL.md
- action: operator-step

## What changed

Every landing now carries the agent skills. `rk init`, `rk adopt`, and `rk upgrade` write each file of `rk-setup` and `rk-release` under `.claude/skills/<name>/` and `.agents/skills/<name>/`, byte for byte as this release carries them. Claude Code reads the first root. Codex, Gemini CLI, and Copilot CLI read the second. The files carry no version stamp. The record lists each file as `rendered`, so `rk status --check` reports a hand edit as drift, and the next `rk upgrade` moves the skills with the pin.

A skill folder that the record does not attribute is never replaced, and `--replace` does not change that. If `.claude/skills/rk-setup/` or another package folder already holds anything other than this release's bytes, the landing refuses and names the folder. `rk adopt` creates the skill files of a package folder that does not exist.

`rk assess` and the classification of `rk status` no longer count a skill copy as evidence of an earlier landing.

Every `rk` command now checks the landing record of its target against the binary before it runs, by a class that each action carries. `rk status`, `rk doctor`, `rk upgrade`, the readers of the method and the skills, `rk runs`, and `rk self-depend` are exempt. `rk init`, `rk adopt`, `rk assess`, `rk profile`, `rk stage`, `rk migrate`, and `rk setup` run on a target with no record. Every other action refuses a target with no record and names `rk init`. Where this binary is newer than the record, a writing action refuses and names `rk upgrade`, and a read-only action runs with one warning line on stderr. Where the record is newer than this binary, the action refuses and names the rk of the project's own environment. A refusal exits 73 and changes nothing. A release that changes no landed file still asks for `rk upgrade`, which then moves only `rk_version`.

The commit-msg hook runs `rk message --check`, which is read-only. A pin move committed before its `rk upgrade` warns and does not block. The release jobs run writing actions, so a pin move without `rk upgrade` stops the next release job until the upgrade lands.

`rk skill install` no longer writes the skills under the home. It prints where the skills come from now and exits 0, and with `--apply` it refuses. Its `--force` and `--scope` flags are gone. `rk skill uninstall --apply` still removes the copies that an earlier release installed under `~/.claude/skills/` and `~/.agents/skills/`. It removes only what the record of that release vouches for, and keeps an edited file. `rk skill show <name> --file <path>` prints one file of a package, such as `references/pre-flight-gate.md`, so an agent in a project with no landing reads the setup skill from the binary.

`rk doctor` drops the probes `skill-roots`, `skill-gate`, and `skill-sources`, and gains `skill-shadow`. It fails while a `SKILL.md` of `rk-setup` or `rk-release` stands under the home, because Claude Code takes a home copy over the project's, and Codex lists both.

## What to do

1. Look for a package folder that the landing would refuse: `ls .claude/skills .agents/skills`.
2. If `rk-setup` or `rk-release` exists there and holds your own files, move those files to a folder of another name.
3. Run `rk upgrade --target . --apply`. It adds both skills under both roots.
4. Run `rk status --check --target .`. It names no skill file.
5. Commit the skill files with the receipt.
6. If a formatter, a Markdown linter, or a spell checker of the project judges `.claude/skills/` or `.agents/skills/`, exclude both folders in that tool's own configuration. The landing owns those bytes, and an edit there is drift.
7. If the project pins rk through a flake input, add `inputs.release-kit.follows = "";` to that input, beside its `url`. From this release on, rk's own flake pins an earlier rk release for its own development. Without the line, `flake.lock` gains a node for that release. The line points that input at the project's own flake, and nothing that the project builds reads it.
8. Move the pin and run `rk upgrade --target . --apply` in one change from now on, so that the release jobs never meet a landing of another release.
9. Run every `rk` command of a project through that project's own environment, for example `direnv exec . rk worktree list`. An rk from another project, or one built from the release-kit tree, refuses a write and names the environment.
10. Once every project that uses rk on the host takes this release, run `rk skill uninstall --apply` once. It removes the home copies that the record of an earlier release vouches for.
11. Run `rk doctor`. Where `skill-shadow` still fails, read each kept `SKILL.md` it names, keep what you need elsewhere, and remove it by hand.
12. Drop `rk skill install` from every install script and recipe.
