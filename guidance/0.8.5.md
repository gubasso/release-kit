# release-kit 0.8.5

- destinations: .release-kit/config.toml, .release-kit/manifest.json, GLOSSARY.md, AGENTS.md, nix/package.nix
- action: operator-step

## What changed

`rk setup step package-check` now faults a Rust target whose published crate ships a file release-kit lands or owns. release-plz attributes a commit to a crate only when the commit changes a file `cargo package --list` prints, so every `rk upgrade` that rewrote `.release-kit/manifest.json` inside the crate asked for a release with no code change, and a packaged `GLOSSARY.md` or `AGENTS.md` did the same whenever a landing rewrote its block. `SECURITY.md` is the one exception, and it must still ship. The check names each packaged path and the `[package].exclude` entry that removes it, and it edits nothing.

Under a record whose release driver is `rust`, `rk integrate` also warns when a `feat`, `fix`, or breaking message integrates a change that touches no packaged file, because release-plz neither lists such a commit in the changelog nor counts it toward a release.

## What to do

Run `rk setup step package-check --target .`. Where it reports unsatisfied, add the entries it names to `[package].exclude` in `Cargo.toml`, where `"/.release-kit"` covers the record and the configuration, or drop them from `[package].include` where the crate uses an allowlist. Run the step again until it reports `ok`. The edit changes `Cargo.toml`, which the crate ships, so release-plz proposes one release for it; every later landing then releases nothing.
